# Repository Instructions

## Configuration Boundaries

- `flake.nix` exposes four `x86_64-linux` outputs: `chi` (Framework 12 laptop),
  `halo` (Strix Halo pubnix server), `misty` (media/storage server), and
  `misty-installer` (installer ISO). Clan Core manages a controller-free
  Mycelium mesh; halo and misty also expose SSH through Iroh.
- `modules/common.nix` is shared by all hosts. chi-only package overlays live in
  `hosts/chi/overlays.nix`.
- `hosts/*/hardware-configuration.nix` is generated by `nixos-generate-config`
  and deliberately excluded from treefmt. Keep it byte-identical unless the
  hardware configuration itself must change.
- `system.stateVersion` and `home.stateVersion` are compatibility pins, not
  release-version markers. Do not bump them during routine input updates.
- `hosts/halo/models-paused.nix` is an opt-in override that removes halo's
  local model services so a build or deploy skips their GGUF closures. It is
  not imported by default; add the import when you need it, and remember that
  deploying with it active stops live inference.

## Verification

- Format and lint with `nix fmt`, then run `nix flake check`. The formatter is
  treefmt with Alejandra, Statix, and deadnix.
- `nix flake check` runs the formatting check and the package self-tests; CI
  separately evaluates the full chi, halo, and misty configs with
  `nix eval --raw .#nixosConfigurations.<host>.config.system.build.toplevel.drvPath`.
- Evaluate every host after changing `flake.nix`, `flake.lock`,
  `modules/common.nix`, or shared inputs.
- Update inputs deliberately with `nix flake update`; review `flake.lock`, then
  rerun formatting, flake check, and the host evaluations before deployment.

## Users And Secrets

- Shared human accounts live under `users/<person>/account.nix` and are opted
  into per host by the roster at `hosts/<host>/users.nix`, which also carries
  the host-specific groups, shell, and SSH keys. The servers use `users/molly`;
  chi keeps the legacy `mollyw` login, declared in `hosts/chi/users.nix`.
- SSH public keys live in `keys.nix` and are referenced by account modules,
  rosters, and installer images — never paste the same key twice.
- Service accounts (`jellyfin`, `qwen`, `niri`, `soju`, …) stay in their
  service modules; do not move them into `users/`.
- Only encrypted SOPS YAML belongs under `secrets/`; never store plaintext there.
  `halo` and `misty` share the encrypted files declared in `.sops.yaml`.
- Locally packaged software lives under `pkgs/`.

## Deployment

- Deploy from chi with `clan machines update` over Iroh/Mycelium; see
  `README.md` and `NETWORK.md`. chi itself uses misty as a Mycelium remote
  builder and is activated locally with `nixos-rebuild`.
- Do not run activation commands unless deployment was explicitly requested.
  Use `build` or `dry-activate` instead of `switch` for a preview.
